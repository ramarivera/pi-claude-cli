## Explicit testing scope

The earlier proposal named protocol fixtures and real host/CLI checks, but didn't explicitly commit to an automated live E2E suite. That commitment is now part of the deferred work tracker. The existing suite mocks subprocesses and host stream implementations; it doesn't contain real authenticated Claude E2E coverage. See [provider tests](/home/ramarivera/dev/pi-claude-cli/tests/provider.test.ts:1) and [process-manager tests](/home/ramarivera/dev/pi-claude-cli/tests/process-manager.test.ts:1).

Recommended coverage layers and acceptance criteria:

| Layer | Required behavior coverage | Evidence it provides |
| --- | --- | --- |
| Improved unit and contract tests | Event parsing/state transitions; full assistant versus streaming deduplication; terminal error variants; permission/control correlation; tool argument semantics; active tool schemas; host-native error/output types; authoritative session IDs; adapter capability fallbacks | Deterministic regression evidence for core and both adapters, including actual host contracts rather than only mocked shapes |
| Versioned protocol replay | Sanitized real NDJSON recordings, labelled by Claude version/flags; init, text/thinking, tools/results, denials/dialogs, retry/rate limits, status/compaction, task/subagent events, resume/interruption; explicit support/ignore decisions for newly observed kinds | Compatibility against captured real wire traffic without inference cost on every run |
| Process integration | Deterministic child process exercising fragmented bytes/UTF-8/lines, malformed input, stderr, EOF without result, EPIPE, late buffered events, abort/result races, timeouts, signal escalation, resource cleanup | Transport/lifecycle behavior beyond mocked spawn calls; clearly labelled as simulated transport |
| Real CLI E2E | Launch and drive the installed authenticated `claude -p`; verify meaningful response, applied system prompt, session continuity, supported failure/cancel behavior, tool handoff and output continuity, no leaked subprocesses/temp files | Executed real Claude protocol evidence; no model mocks in this layer |
| Real host E2E | Load the actual Pi or OMP entrypoint into each host's programmatic/headless runtime and execute through the extension into real `claude -p`; verify built-in/custom tool execution ownership, native argument format, result round-trip, active tool policy, resume and lifecycle cleanup | Both entrypoints and their shared-core boundary actually work together |

Live tests must assert observable semantics and execution counts, not merely that Claude launched or stdout wasn't empty. A tool test should use a bounded local sandbox/sentinel and establish who executed it and that it executed exactly once. Pi and OMP need separate assertions for their effective schemas, especially OMP edit modes and tool formats. Mixed Claude-internal/host tool rounds need explicit ownership coverage too.

Use an explicit opt-in environment gate (proposed name: `PI_CLAUDE_LIVE_E2E=1`), configurable CLI/model selection, an isolated test directory, and bounded turns/tokens/time; use spend controls where the transport/account supports them. Exact variables and supported limits will be designed during implementation. Don't promise a dollar ceiling enforced by a token limit. Start with a small smoke suite and a broader manual/scheduled suite, record versions and sanitized artifacts, and surface usage/cost where available. Disabled means visibly skipped; enabled but missing CLI/auth should fail with the prerequisite error. A passing mocked/replay suite must never be reported as passing live E2E. No such tests were executed in this research turn.

## What T3 and BB actually use

Both Claude providers wrap `@anthropic-ai/claude-agent-sdk` using `query()` and async prompt/message streams. The SDK drives the Claude Code executable; these provider modules don't hand-build raw `claude -p` argv or call the Anthropic Messages API as their Claude Code transport. T3 explicitly passes the resolved executable path. BB supplies SDK executable options and uses SDK session APIs. Their final SDK-generated argv wasn't inspected; don't describe their integration as the same raw subprocess implementation this extension has. [T3 SDK imports](https://github.com/pingdotgg/t3code/blob/c18e5ea6ed741443a8ec4a5d22d4b6939b0ecd21/apps/server/src/provider/Layers/ClaudeAdapter.ts#L12), [T3 query/options](https://github.com/pingdotgg/t3code/blob/c18e5ea6ed741443a8ec4a5d22d4b6939b0ecd21/apps/server/src/provider/Layers/ClaudeAdapter.ts#L4910), [BB query](https://github.com/get-bb/bb/blob/facb6c161d9915d2517ed15f6101e4295cf85da1/plugins/provider-claude-code/src/bridge/sdk-session.ts#L235).

### Recommended design takeaways

1. Follow T3's neutral event contract boundary: normalized events with source attribution, optional raw diagnostic payload, and explicit request/task/terminal lifecycles. Keep credential-bearing diagnostics redacted. [Event contract](https://github.com/pingdotgg/t3code/blob/c18e5ea6ed741443a8ec4a5d22d4b6939b0ecd21/packages/contracts/src/providerRuntime.ts#L23), [adapter boundary](https://github.com/pingdotgg/t3code/blob/c18e5ea6ed741443a8ec4a5d22d4b6939b0ecd21/apps/server/src/provider/Services/ProviderAdapter.ts#L67).
2. Reuse the stream/snapshot reconciliation and explicit session/request state patterns, without copying T3's large adapter wholesale. Core events can be shared; Pi/OMP output objects and capability behavior stay in adapters.
3. Separate process lifetime from model-turn lifetime. BB's runtime owns bridge-process cleanup while its provider owns SDK-session cleanup. Here the core should own Claude subprocess/resources and each adapter should tie that lifetime to the host. [BB process ownership](https://github.com/get-bb/bb/blob/facb6c161d9915d2517ed15f6101e4295cf85da1/packages/agent-runtime/src/runtime-provider-process.ts#L375).
4. Evaluate resident sessions and prompt queues for continuity/steering, but validate host tool-result handoff before choosing them. Current extension deliberately stops Claude for supported host tools; T3 normally lets Claude execute its own tools. BB forwards injected host tools through SDK MCP callbacks. Execution policy cannot be copied unchanged. [BB tool proxy](https://github.com/get-bb/bb/blob/facb6c161d9915d2517ed15f6101e4295cf85da1/plugins/provider-claude-code/src/bridge/tool-proxy-mcp.ts#L27), [current handoff](/home/ramarivera/dev/pi-claude-cli/src/provider.ts:257).
5. Use the SDK as a typed protocol/reference implementation for this research. Moving this project from raw CLI to SDK would be a separate transport/dependency decision; the present proposal keeps direct `claude -p`.
6. Give unknown or deliberately ignored payload families explicit handling/diagnostics, with compile-time exhaustiveness where types support it and runtime tolerance for additive fields/events. Typed SDK definitions don't cover every observed wire field.

## Native default OMP Anthropic subscription transport

Observed source for OMP 18.4.4 at the pinned commit above:

1. `/login anthropic` uses OMP's OAuth flow: authorize at Claude.ai, exchange/refresh with Anthropic, then store/select the token through OMP auth. This isn't a Claude CLI login subprocess. [Auth rule](https://github.com/can1357/oh-my-pi/blob/2b023d1b80133c523d66412602d99b5427408395/packages/catalog/src/compat/rules/auth/anthropic.kdl#L6), [auth priority](https://github.com/can1357/oh-my-pi/blob/2b023d1b80133c523d66412602d99b5427408395/packages/ai/src/auth/cascade.ts#L305).
2. The built-in Anthropic provider invokes OMP's own HTTP Messages client. OAuth requests go to `POST https://api.anthropic.com/v1/messages?beta=true` by default. It does not delegate inference to `claude -p`. [Provider registration](https://github.com/can1357/oh-my-pi/blob/2b023d1b80133c523d66412602d99b5427408395/packages/ai/src/providers/register-builtins.ts#L236), [client routes](https://github.com/can1357/oh-my-pi/blob/2b023d1b80133c523d66412602d99b5427408395/packages/ai/src/providers/anthropic-client.ts#L191), [default endpoint](https://github.com/can1357/oh-my-pi/blob/2b023d1b80133c523d66412602d99b5427408395/packages/ai/src/providers/anthropic-client.ts#L237), [OAuth invocation](https://github.com/can1357/oh-my-pi/blob/2b023d1b80133c523d66412602d99b5427408395/packages/ai/src/providers/anthropic.ts#L2535).
3. OAuth headers deliberately use the Claude Code fingerprint: Bearer token, `claude-cli/<version> (external, cli)` user agent, `x-app: cli`, Claude Code/Stainless headers and betas. OMP also shapes system/billing fields locally. These aren't requests constructed by the published Claude executable. [Headers](https://github.com/can1357/oh-my-pi/blob/2b023d1b80133c523d66412602d99b5427408395/packages/ai/src/providers/anthropic.ts#L389), [fingerprint defaults](https://github.com/can1357/oh-my-pi/blob/2b023d1b80133c523d66412602d99b5427408395/packages/ai/src/providers/claude-code-fingerprint.ts#L15), [local request shaping](https://github.com/can1357/oh-my-pi/blob/2b023d1b80133c523d66412602d99b5427408395/packages/ai/src/providers/anthropic.ts#L634).
4. `/api/claude_cli/bootstrap` is an account/org lookup after OAuth, not the model-chat endpoint. No local Claude CLI signing process was found on this path. References to signing proxies concern remote endpoint compatibility/thinking signatures. [Bootstrap](https://github.com/can1357/oh-my-pi/blob/2b023d1b80133c523d66412602d99b5427408395/packages/ai/src/registry/oauth/anthropic.ts#L46), [proxy classification](https://github.com/can1357/oh-my-pi/blob/2b023d1b80133c523d66412602d99b5427408395/packages/catalog/src/compat/anthropic.ts#L49).

This extension supplies such a custom transport; compatibility with current OMP remains to be implemented and exercised. ## Current Anthropic policy distinction

Ramiro's follow-up clarification: official Agent SDK subscription authentication and `claude -p` must be distinguished from a third-party HTTP client advertising Claude Code's identity. For an end user driving the published Claude runtime with their own subscription, both the official SDK and `claude -p` are covered by Anthropic's current subscription guidance. Using the SDK isn't itself impersonation. Developer products that collect/intermediate users' tokens remain a separate policy question; don't apply that restriction indiscriminately to personal SDK/CLI use. [Current SDK/subscription guidance](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan), [published-binary exception](https://code.claude.com/docs/en/legal-and-compliance).

Calling the Messages endpoint isn't inherently prohibited; API-key/cloud access is the supported third-party route. Anthropic's current authentication guidance prohibits third-party tools that misrepresent their identity or route third-party traffic against subscription limits. OMP's default OAuth code advertises a Claude Code identity; that is the relevant policy concern, and absent separate Anthropic permission I wouldn't treat it as an approved subscription integration. No OMP-specific approval was established. [Authentication guidance](https://support.claude.com/en/articles/13189465-log-in-to-your-claude-account).

Anthropic's Claude Code policy distinguishes developers handling subscription credentials from end users signing into the unmodified published Claude Code binary with their own subscription; the latter is explicitly allowed, subject to the applicable terms. This supports preferring the real CLI boundary here, while leaving the user's login inside Anthropic's software. It doesn't make every third-party product/auth design automatically compliant. [Claude Code legal/authentication policy](https://code.claude.com/docs/en/legal-and-compliance).

Current SDK billing guidance includes a June 15 update pausing the earlier announced changes: SDK and `claude -p` usage still count against subscription limits for now. The historical credit plan beneath that update isn't operative guidance. API-key inference remains billable; live tests consume real account resources regardless. [Agent SDK plan update](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan).
